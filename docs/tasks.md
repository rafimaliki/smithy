Scope: the build plan as briefs an agent can pick up cold. Read `AGENTS.md`, `docs/stack.md` and `docs/features.md` first; this file only adds what each task needs.

# How to work a task

- **The design is in framery, not in code.** The board is `framery/smithy`. Read the frames named in your brief before writing UI: `npx framery cmd outline '{"page":"flows"}'` lists every frame with its description and arrows; the HTML of a frame is at the `src` path it prints (`framery/smithy/flows/...`). Theme tokens are the `theme-tokens` table on page `themes`; file icons are on page `icons`. Never edit board files by hand. If the design is wrong or missing something, say so in the PR instead of inventing a screen.
- **The plan is a framery table**: page `plan`, table `impl-plan`, one row per task (row ids below). Read it to see what is built and what your task needs. **Do not edit it**: the whole table is one line in `framery/smithy/pages/plan.json`, so parallel edits always conflict. The orchestrator updates the status cells from open and merged PRs.
- **One task, one branch, one PR.** Branch `feat/<row id>`, commits `feat: <what>` (lowercase imperative, no attribution trailer), open the PR with `gh pr create` with a body of what / why / test plan. Never push to `main`. Never merge: the orchestrator merges after review.
- **Build commands**: `cargo fmt`, `cargo clippy --all-targets -- -D warnings`, `cargo test`. Rust is at `~\.cargo\bin` (prepend it to PATH). Use the shared target dir so gpui is not rebuilt: `CARGO_TARGET_DIR=C:/Files/Source-Code/Non-Kuliah/VibeProjects/smithy/target`. Do not run `cargo build --release` unless the brief says so.
- **gpui 0.2.2 API: read the crate source, never guess.** It is in `~\.cargo\registry\src\index.crates.io-*\gpui-0.2.2\src` (examples in `..\examples`). Compile early and often; a method that does not exist is the most likely failure.
- **Where code goes**: a core feature goes in its domain folder (`src/editor`, `src/tree`, `src/workspace`). An add-on is one new module in `src/addon/` (copy `src/addon/image_viewer.rs`; register it in `all()` in `src/addon/mod.rs`; split into a folder when it passes the file ceiling). An add-on must not run code, spawn threads or allocate caches until `Addon::start` is called, and must free everything when its instance is dropped.
- **Rules from AGENTS.md apply**: surgical diffs, 300-line soft / 500-line hard file ceiling, one responsibility per file, shortcuts marked `// ponytail: <ceiling>, <upgrade path>`. Tests only where a plausible bug would fail them (pure logic: parsers, diff math, ordering); mirror the source tree; no tests of gpui rendering.
- **Do not touch files outside your task** except the one-line registration in `src/addon/mod.rs` and the `Cargo.toml` dependencies you add (pick the lightest crate; justify any heavy one in the PR).
- **Definition of done**: fmt, clippy and test pass; you launched the app (`cargo run`) and exercised your feature by hand where the environment allows, and say in the PR what you saw and what you could not check; the PR is open and says what you saw.

# Measuring the core build

After any core task, with an add-on-free build and one folder open, record the numbers in the PR: release build, idle working set (`Get-Process smithy | % WorkingSet64`), time to first window. Targets are in `docs/stack.md`.
